# FinancialEmpire

一个基于 **PyQt5** 的单标的**多主体交易市场模拟器**。

20 个自动交易者在虚拟交易所中完整经历「**IPO 申购 → 摇号配售 → 二级市场连续竞价撮合**」的全过程，
界面以逐笔播放的方式实时展示**买卖盘深度**与**价格走势曲线**，用于观察微观结构下的价格形成机制。

---

## 功能特性

### 交易所（撮合核心）
- **交易者管理**：注册交易者并绑定交易所，统一维护资金、持仓、挂单。
- **IPO 发行**：设定发行价与发行总股数；股数默认按人均 500 股随交易者数量自动缩放，
  避免人数增加时交易者总现金淹没固定的股票供给、把价格推到失真区间。
- **IPO 申购**：按发行价冻结申购资金，资金不足时自动缩量。
- **摇号配售**：完整实现打新算法 —— 统计认购倍数，申购不足则全额中签；超额则打乱顺序随机抽签，
  随后多轮补充分配直至分完（最多 10 轮，防死循环）；中签发股、未中签全额退款、冻结资金多退少补。
- **下单校验**：买单校验现金、卖单校验持仓，**禁止做空**。
- **资金/持仓冻结**：买单冻结现金，卖单冻结持仓，撤单时原路退回。
- **价格-时间优先撮合**：买价 ≥ 卖价即可成交，成交价取**先挂单方（order_id 较小）的报价**，
  同价按 **FIFO**；买方按价差退回多冻结的资金。
- **市场数据**：按价位聚合的多档盘口快照、最新成交价、完整成交流水。
- **诊断输出**：摆盘打印、交易所状态打印、全局汇总打印。

### 订单簿
- 双堆实现，插入 O(log n)：买盘用 `-price` 构造最大堆，卖盘最小堆，`order_id` 作第二排序键。
- 取最优价时惰性弹出已失效订单，快照输出「价位 + 该价位总量 + 各订单明细」。

### 交易者智能体
- **预期价格模型**：每隔随机 1–5 轮，在最新价 **±10%** 区间内重新生成预期价；
  仅当预期价**发生变化**时才触发交易决策，避免无意义下单。
- **决策规则**：
  | 持仓 | 观点 | 动作 |
  |---|---|---|
  | 无持仓 | 看涨（预期 > 最新价） | 按预期价下买单 |
  | 无持仓 | 看跌（预期 < 最新价） | 挂低价买单等待回调 |
  | 有持仓 | 看跌 | 按预期价下卖单 |
  | 有持仓 | 看涨 | 挂高价卖单等待拉升 |
- **挂单管理**：每个标的最多保留一张活跃挂单；价格或方向不一致时自动撤单重挂；
  下单数量按可用资金（含已冻结部分）或可用持仓计算。

### 预期价可视化
- 收集方式刻意做成**按轮次聚合**而不是逐笔事件流：每轮只落下一行分位数
  （p10 / 中位数 / p90）和一个固定分辨率的价格直方图，
  因此**存储与渲染成本都不随交易者数量增长**，交易者数量从几十调到几千无需改渲染代码。
- 主视图为「轮次 × 价格」密度图：交易者很少时图形自然退化为散点，
  数量变大后过渡为密度云。
- 叠加 p10–p90 分位带与中位数线，并画出最新价作为参照；
  顶部状态栏同步显示预期中位数及其相对最新价的偏离。
- 交易者每轮会被随机打乱，但快照矩阵的列按 `trader_id` 固定映射，
  因此同一个交易者在整张图上始终占同一行。

### 图形界面（深色交易终端风格）
- **主窗口**：开始/继续、暂停、重置；1–8x 速度滑块；轮次进度、最新价（涨红跌绿）、成交笔数、最新成交明细、预期中位数。
- **参数栏**：交易者数量、总轮次、发行价、发行数量四个输入框（发行数量留空 = 按人均 500 股自动缩放）。
  点「开始」后整组输入框**与标签一起置灰锁定**，只有点「重置」才重新解锁；
  非法输入回退到上次生效值，越界值自动夹取并写回输入框。
- **布局**：左侧摆盘，右侧上下分栏为价格曲线与预期分布，分隔条可自由拖动。
- **摆盘视图**：自绘 8 档深度，卖盘在上、买盘在下，中间高亮最新价并显示**价差**与**较发行价涨跌**；
  数量条按 `OrderBookView.BAR_WIDTH_RATIO`（默认 0.7）留出右侧余白。
- **价格曲线**：自绘坐标轴与网格，刻度自适应；黄色虚线为 IPO 发行价基准；面积填充 + 播放头实时标示进度。
- **预期分布图**：横轴轮次、纵轴价格，亮度表示该价位上的预期人数；叠加分位带、中位数线与最新价，
  用于观察全市场预期的共识价位与分歧程度。
- **尺寸记忆**：窗口尺寸与三块面板（摆盘 / 价格走势 / 预期分布）的尺寸都写入
  `Src/Config/config.json`，下次启动按记录值还原（窗口尺寸会裁剪到当前屏幕可用区域）。
- 定时器 80ms 一帧，按速度倍率每帧推进多步；无变化的空步会被自动跳过，画面不会停顿。

### 配置持久化
窗口尺寸与三块面板（摆盘 / 价格走势 / 预期分布）的尺寸都会被记住：手动拖拽结束后自动记录，
下次启动按记录值还原；文件位于 `Src/Config/config.json`。

```json
{
  "window": {
    "width": 1320,
    "height": 880
  },
  "layout": {
    "main_splitter": [435, 856],
    "right_splitter": [371, 365]
  }
}
```

`main_splitter` 是左右两栏（摆盘 | 右侧），`right_splitter` 是右侧上下两栏（价格走势 | 预期分布）。
这些默认值是按默认窗口大小（1320×880）调好的；窗口更大时多出的空间仍由 `stretchFactor`
（4:6 与 3:2）分配。任一项写成 `null` 表示不干预、完全交给 `stretchFactor`。

- **首次启动即生成**该文件（含默认值），之后按需更新；所以目录和文件不会等到第一次拖拽才出现。
- 窗口尺寸**下限不自行设置**，交给布局的最小尺寸（`minimumSizeHint`，当前 868×574）兜底。
  若再自设一个更大的下限，用户把窗口缩到布局下限后关闭，下次启动会被抬得比离开时更大。
  已验证：窗口显示时 Qt 会用布局下限兜住过小的记录值（记录 10×10 也会显示为 868×574）。
- 分割器尺寸必须在布局生效之后才能套用——`QSplitter.setSizes()` 过早调用会被直接丢弃，
  因此还原动作由 `showEvent` 推迟到下一轮事件循环，且只在首次显示时执行一次。
- 面板尺寸小于各自最小尺寸时会被 Qt 顶回：摆盘 360×420、价格走势与预期分布 480×220，
  所以还原值可能与记录值有偏差（例如记录 `[537, 209]` 实际还原为 `[526, 220]`）。
- `layout` 段里尺寸的个数与分割器面板数不一致时**安全放弃**（回落 stretchFactor），
  避免以后改动布局后读到旧配置而错位。
- 配置里的数值合计与当前可分配空间不一致时（换了窗口大小、或换了环境导致行高不同），
  多出/缺少的空间由 `stretchFactor` 分配，**配置文件本身不会被改写**——
  只有用户实际拖动窗口或分割条才会重新记录，所以尺寸不会随启动次数漂移。
- 读写由 `Src/Main/Core/ConfigManager.py` 统一管理（该类不依赖 Qt，屏幕裁剪等界面逻辑留在调用方）。
- 新增一项配置只需两步：在 `ConfigManager.DEFAULTS` 里加 `section -> key -> 默认值`，
  再用 `get` / `set` 读写。类型校验以默认值类型为准；默认值为 `None` 的项（分割条尺寸）
  只接受非空的整数列表。
- 健壮性：文件缺失、内容损坏、类型不符都会回退到默认值并记一条 WARNING 日志；
  写入先落临时文件再原子替换，避免中途崩溃留下半个文件。
- 文件已存在但内容损坏时**不会主动覆盖**（只在内存中回退默认值），保留手动查看和修复的余地。

### 日志
- 4 个级别（DEBUG / INFO / WARNING / ERROR），格式 `时间 | 级别 | 内容`。
- 内存缓存 500 条后批量落盘，支持强制刷盘（暂停、重置、关闭窗口时触发）。
- 日志文件位于 `Src/Logs/FELog_日期(时分秒).txt`。

## 核心机制说明

### 撮合规则
1. 取买盘最高价与卖盘最低价，若**买价 < 卖价**则停止撮合。
2. 成交量为双方剩余量的较小值。
3. 成交价取**先挂单方**的报价（`order_id` 较小者视为被动方）。
4. 买方若出价高于成交价，差额部分退回其账户。
5. 更新最新成交价并生成成交记录，循环继续直到无法撮合。

### 下单与 IPO 的边界
- `Exchange.submit_order` 只处理**二级市场**的下单、校验、冻结与撮合，**不区分 IPO 阶段**。
- IPO 申购与配售一律走 `apply_ipo` / `allocate_ipo`，与二级市场链路互不干扰。
- `ipo_completed` 仅用于状态展示（`Exchange.print_status`），不参与任何下单校验。

### IPO 配售算法
1. 计算认购倍数 = 总申购量 / 发行总量。
2. **申购不足**：所有申购者全额中签。
3. **超额申购**：打乱申购顺序，依次随机抽取中签数量（上限与认购倍数负相关），
   任一环节剩余股数耗尽则后续申购者无法中签。
4. 若第一轮后仍有剩余，进入**补充分配**多轮循环，在仍有申购额度的人之间随机分配。
5. 结算：中签者获得股票并退还多余冻结资金，未中签者全额退款。

### 可调参数
交易者数量、总轮次、发行价、发行数量四项可在界面参数栏直接填写；
其余参数集中在 `Src/Main/GUI/MarketSimulation.py`：

| 参数 | 默认值 | 说明 |
|---|---|---|
| `NUM_TRADERS` | 20 | 交易者数量 |
| `SYMBOL` | `AAPL` | 交易标的 |
| `IPO_PRICE` | 100 | 发行价（整数） |
| `IPO_SHARES` | 自动 | 发行总股数；留空时按人均股数随人数自动缩放 |
| `IPO_SHARES_PER_TRADER` | 500 | 每名交易者对应的发行股数 |
| `MAX_ROUNDS` | 100 | 模拟总轮次 |
| `BOOK_DEPTH` | 8 | 盘口档位深度 |
| `DENSITY_BINS` | 120 | 预期分布图的价格分桶数 |
| `DENSITY_LOW_RATIO` / `DENSITY_HIGH_RATIO` | 0.3 / 3.0 | 分桶范围（相对发行价） |

交易者数量与轮次也可以在构造时指定，无需改类常量：

```python
sim = MarketSimulation(num_traders=500, max_rounds=200)
```

发行股数默认按 **人均 500 股** 随人数自动缩放。交易者总现金大致随人数线性增长，
若发行股数固定不变，「总现金 / 总股数」会随人数一起抬升，价格会被资金推高到失真区间
（实测：股数固定 10000 时，T=20 收盘价约 80，而 T=300 约 3000）。
需要固定发行股数时显式覆盖即可：

```python
sim.IPO_SHARES = 10000   # 覆盖自动缩放
```

`MainWindow` 目前使用默认值，改动入口在这里：

```python
self.sim = MarketSimulation(num_traders=500, max_rounds=200)
```

其余参数：初始资金服从对数正态分布（目标均值 10 万，截断于 1 万–1000 万）；
IPO 申购比例为可用资金的 50%–80%；价格全部使用**整数**，避免浮点精度问题。

## 已知行为约定与后续计划

**行为约定**
- `Exchange.submit_order` 不区分 IPO 阶段，IPO 申购/配售与二级市场撮合是两条独立链路。
- `ipo_completed` 目前仅用于状态展示（`Exchange.print_status`），不再参与下单校验。
- 预期价的更新间隔实际为 **1–5 轮**随机（`random.randint(1, 5)`）。
- 预期价按轮次聚合存储，不保留逐笔事件流，因此其存储与渲染成本与交易者数量无关。
- 预期价刻意**不参与** `_fingerprint()` 比对：否则几乎每一步都会被判定为"有变化"，
  逐笔播放会退化为每帧只走一个交易者。
- 预期价快照矩阵的列按 `trader_id` 固定映射，而非遍历下标——交易者每轮都会被 `shuffle`。
- 发行股数默认按人均 500 股随交易者数量缩放，使「总现金 / 总股数」与人数无关；
  显式设置 `IPO_SHARES` 可覆盖该行为。
- 参数输入区的锁定判据统一为 `phase == "idle"`：开始后进入 `trading`、跑完停在 `done`
  都保持锁定，**只有重置回到 `idle` 才解锁**。因此暂停后想改参数必须先放弃当前运行。
- 运行期间参数只由输入框在 `idle` 态决定，`_read_params()` 的写回（越界夹取）在控件被禁用时
  依然有效——`setEnabled(False)` 只拦截用户输入，不拦截程序化的 `setText()`。

**已知限制**
- 模拟未设置随机种子（`random` 与 `np.random` 均未固定），相同参数下每次运行的
  成交笔数与价格路径都不同，结果不可复现。
- `_fingerprint()` 每次都重建整个盘口快照，`snapshot()` 每帧都全量拷贝 `price_points`，
  这两处在交易者数量上千后会成为性能瓶颈（尚未处理）。
- 界面上的交易者数量上限为 **2000**（`MainWindow.PARAM_LIMITS`）。正因为上面两条未处理，
  人数再往上会把界面拖死，所以刻意收紧。
